# Conformance

How this repository proves the Flutter renderer derives the same values as the React and Angular
renderers, and how to regenerate the evidence when upstream changes.

Background: [ARCHITECTURE.md § 10](ARCHITECTURE.md#10-the-conformance-suite).

---

## Why this exists

[ADR-003](https://github.com/daivahealth/openmedform/blob/main/docs/ADR/003-json-forms-platform.md)
requires every renderer to derive every value identically — a control that computes a score
differently in one framework means the same form reads differently in the EMR than in the web app.
Upstream, that obligation is currently held by prose comments asserting parity and by per-framework
tests. That does not survive a third implementation in a different language: nothing would catch a
Dart port that rounds a subtotal differently or treats an empty string as present.

So the parity contract is written down as data. The fixtures below are generated by calling the real
TypeScript implementation, and the Dart tests replay them. A divergence fails CI instead of reaching
a clinician.

## Comparison rules

Three places where a naive comparison would produce false failures:

**`undefined` is encoded explicitly.** JSON has no `undefined`, but Dart distinguishes an absent key
from a null one, and so does the TypeScript being ported (`readRecordPath({}, …)` returning
`undefined` is a different assertion from returning `null`). Every fixture declares
`"undefinedMarker": "__undefined__"`, and that string stands for `undefined` in both `args` and
`expected`.

**Numbers widen to `num` before comparing.** JavaScript has only `double`; Dart distinguishes `int`
from `double`, so a value that round-trips as `1` in one language may be `1.0` in the other. Compare
numerically, never by runtime type.

**Validation compares `valid` plus `(instancePath, keyword)` pairs — never message text.** Ajv's
messages are specific to Ajv; no Dart validator will reproduce them, and requiring it would
guarantee a permanently red suite while testing nothing clinically meaningful. What matters is
*whether* a payload is valid and *which field failed which keyword*. The error lists are sorted, so
ordering differences do not register as failures. `conformance_fixtures_test.dart` asserts the
fixtures carry no message text, so this rule cannot quietly erode.

## Regenerating

The generator is [`tool/conformance_export.ts`](tool/conformance_export.ts). It is TypeScript and
does not run in this repository — it runs inside the openmedform monorepo, which owns `form-core`
and its Ajv dependency. It is shaped as a vitest test because `form-core` ships ESM TypeScript with
no build output, and vitest is the only runner already wired up for it.

```bash
OMF=/path/to/openmedform
FLU=/path/to/openmedform-flutter

cp $FLU/tool/conformance_export.ts $OMF/packages/form-core/src/__conformance_export.test.ts
cd $OMF/packages/form-core
OMF_FIXTURE_OUT=$FLU/packages/openmedform_form_core/test/conformance \
OMF_SOURCE_SHA=$(git -C $OMF rev-parse HEAD) \
  ./node_modules/.bin/vitest run src/__conformance_export.test.ts
rm $OMF/packages/form-core/src/__conformance_export.test.ts
```

Then update the pinned SHA in the table above, and check `git status` in the monorepo is clean — the
generator is copied in and removed again, and should leave nothing behind.

Staging a TypeScript file in a Dart repository is a stopgap. The intended end state is a proper
script in `form-core` that emits these fixtures as part of the monorepo's own test run, so parity
data regenerates whenever upstream behaviour changes rather than whenever someone remembers. That is
tracked as a follow-up in [PLAN.md](PLAN.md#follow-ups-in-the-openmedform-monorepo).

## Known divergences

Every accepted difference is written down here with its justification. A gap recorded here is a
decision; a gap not recorded here is a bug.

### Deferred, not divergent

**`serializeForSubmit` (2 cases, skipped).** It validates against the data schema, so it lands with
the validator in M2 (#3). The test run reports these as skipped with that reason attached rather
than passing silently.

### Adaptations required by the language

**List indexing in `getValueAtPath` and `readRecordPath`.** JavaScript indexes arrays with string
keys, so the original walks into an array without any special case. Dart cannot, so the numeric
parse is explicit. Behaviour is the same; only the implementation differs. Record-table paths such
as `treatments.0.date` depend on it, and it is covered by tests outside the fixtures because the
TypeScript tests never exercised it either.

**Whole doubles print without a decimal point.** JavaScript's `String(2.0)` is `"2"`; Dart's
`2.0.toString()` is `"2.0"`. A dose that round-trips through JSON as a double would otherwise read
differently here than in the web renderer, so `recordCellText` formats whole doubles as integers.

**Writes into a list are not supported by `setValueAtPath`.** An intermediate that is a list gets
replaced by a map, because the original's plain-object check excludes arrays. This is faithful to
the TypeScript rather than a Dart limitation, and it is the reason the record table rebuilds arrays
itself. Worth remembering at M5 (#6).

### Upstream inconsistencies preserved deliberately

**Three humanization rules, not one.** For a property with no `title`, the platform humanizes keys
three different ways:

| source | `insertedBy` | `spo2Reading` |
|---|---|---|
| print engine `controlLabel` | `Inserted By` | `Spo2Reading` |
| `humanizeKey` (record-table columns) | `Inserted by` | `Spo2 reading` |
| lodash `startCase` (JSON Forms' own) | `Inserted By` | `Spo 2 Reading` |

Each is ported as a separate function matching its own call site, and the record-table variant is
pinned by fixtures. Unifying them would be an upstream behaviour change affecting the web renderers,
not something to decide inside a port. Flagged as a follow-up in
[PLAN.md](PLAN.md#follow-ups-in-the-openmedform-monorepo).
